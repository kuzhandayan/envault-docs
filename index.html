envault securely syncs your .env files across laptops using your own private GitHub repo as storage. Everything is encrypted on your machine before it ever leaves — not even GitHub, and not envault itself, can ever see your real values.

01 How It Works (Read This First)

  • Two independent locks protect your secrets:
    • GitHub token — controls who can access the encrypted files.
    • Master password — controls who can decrypt them.
    Both are required. Neither alone is enough.
  • Your master password is never stored anywhere — not on your disk, not on GitHub, not encrypted, nowhere. It only exists in memory while a command runs.
  • Only encrypted ciphertext ever leaves your laptop. GitHub only ever sees meaningless-looking encrypted blobs.
  • All encryption/decryption happens locally on your machine — GitHub does zero computation, it's just storage.
Critical If you forget your master password, your data cannot be recovered. Treat it like a crypto wallet seed phrase.

02 Installation

npm install -g envault-sync

Published on npm as envault-sync, but this installs the envault command itself — every command below is typed as envault ..., not envault-sync ....

If running from source instead of a global install:

node bin/envault.js <command>

03 First-Time Setup — envault init

envault init

What it asks for, in order:

  1. GitHub Personal Access Token — needs repo scope. Generate one at github.com → Settings → Developer settings → Personal access tokens → Tokens (classic) → Generate new token (classic).
  2. A master password — must be 12+ characters, with uppercase, lowercase, a number, and a symbol.
  3. A 4-digit security PIN — needed later, together with your password, to change your master password.

What it does automatically:

  • Creates a private GitHub repo called envault-store (only on true first-time setup — if one already exists, it reuses it).
  • Clones it to ~/.envault/store on your machine.
  • Generates a random salt, saves your config to ~/.envault/config.json (permissions locked to owner-only).
  • Encrypts a small "verify" file and your PIN's verify file, pushes everything.

Re-running init later (new laptop, or refreshing an expired token)

If you run init again and envault-store already has data in it, it switches into recovery mode:

  • Asks for your existing master password (not a new one) and checks it against the data already in the repo.
  • Correct password → everything works, nothing is touched or reset.
  • Wrong password → aborts cleanly, nothing changed.
  • It does not ask for a new PIN in this case — your original one carries over.

If you forget your master password

No recovery — by design Your only path forward is to abandon that repo (rename or delete envault-store on GitHub) and run init fresh with a new password. Old encrypted secrets remain permanently inaccessible.

04 Push / Pull — Whole File

envault push <project> --env <envName>              # encrypts ./.env and pushes it
envault push <project> --env <envName> --file <path> # use a specific source file

envault pull <project> --env <envName>               # pulls + decrypts into ./.env
envault pull --all                                    # restores everything into a folder you choose

Example:

cd ~/code/myapp
envault push myapp --env dev
# ...on another laptop:
envault pull myapp --env dev

--env names are completely free-form (dev, production, uat, qa, whatever you use) — not a fixed list. Re-pushing to the same project+env always fully replaces the previous content — no duplication, no merging of old and new, a clean overwrite every time.

05 Managing Projects & Environments

envault env create <project> <envName>     # create a new empty environment
envault env list <project>                 # list environments for a project
envault env delete <project> <envName>     # delete one environment (asks to confirm)

envault project list                       # list all projects + their environments
envault project delete <project>           # delete a project and ALL its environments (asks to confirm)

A project is the top-level bucket (e.g. myapp); every environment you create for it (dev, uat, production, or any name you choose) lives inside that same bucket, but each environment's data stays fully separate from the others unless you deliberately combine them (see Merge below).

06 Combining Multiple Files Into One Environment — envault merge

envault merge <project> --env <envName> --file <path1> --file <path2> [--file <path3> ...]

Combines 2 or more .env files into a single environment. If the same key appears in more than one file with different values, you're prompted interactively to resolve it — nothing is silently overwritten. If a key appears in multiple files with the same value, that's not treated as a conflict.

Options when a conflict is found:

  • Keep the existing value
  • Use the new (incoming) value
  • Keep both — renames the incoming one (e.g. API_KEY → API_KEY_ALT) so neither value is lost
  • Enter a completely custom value

Example:

envault merge myapp --env live_qa --file src/.env --file src/.env.uat

07 Interactive Editing — envault edit

envault edit <project> --env <envName>

Decrypts the environment into a temporary file, opens it in your terminal's text editor (whatever $EDITOR is set to, e.g. vim, nano — defaults to nano if unset), and lets you freely add, change, or delete lines exactly like editing a normal file. When you save and close the editor, it automatically re-encrypts and pushes the result. If you close without changing anything, nothing is pushed. The temporary plaintext file is deleted immediately afterward either way.

This only edits the content of the one environment you specify — it cannot rename the environment, rename the project, or touch any other environment in the same session.

08 Key-Level Editing (No Full File Overwrite)

Edit a single key inside an already-pushed environment without touching the rest:

envault set <project> --env <envName> KEY=VALUE     # add or update one key
envault get <project> --env <envName> KEY           # print one key's value
envault delete-key <project> --env <envName> KEY    # remove one key
envault list-keys <project> --env <envName>         # list key NAMES only (values hidden)

set handles both adding a brand-new key and updating an existing one — same command either way. Everything else in that environment stays untouched.

09 Discovery & Convenience Commands

envault scan [--path <dir>]     # finds all .env* files under a folder, shows a
                                 # checklist, lets you pick which to push
envault view <project> --env <envName>    # decrypt and print to terminal ONLY (never writes to disk)
envault copy <project> --env <envName>    # decrypt and copy to clipboard (never touches disk)
envault list                              # table of every project + env + last updated time

scan is the fastest way to onboard an existing project — it automatically detects the project name from the nearest .git folder and guesses the environment name from the filename:

  • .env → environment dev (the one special case)
  • .env.<anything> → environment <anything> (used verbatim)

It always shows a tick-list before pushing anything — even with just one file found — so nothing gets uploaded without an explicit confirmation.

10 Changing Your Master Password — envault change-password

envault change-password

Requires, in order:

  1. Your current master password (verified against your existing data)
  2. Your security PIN (set at init time) — an extra confirmation layer
  3. A new master password (with the same strength rules)
  4. A new PIN (for the next time you change it)

Every stored secret is decrypted with your old key and re-encrypted with the new one — nothing is lost. If the push to GitHub fails partway through (e.g. no internet), everything is automatically rolled back to exactly how it was.

11 Non-Interactive / CI Use

Set the ENVAULT_PASSWORD environment variable to skip the interactive password prompt on any command that needs to decrypt something:

ENVAULT_PASSWORD="your-master-password" envault pull myapp --env production

13 Security Summary

  • Encryption: AES-256-GCM. Key derivation: scrypt.
  • GitHub only ever stores ciphertext.
  • No central server, no shared database — every user is fully isolated with their own repo.
  • As secure as a well-managed password manager — not immune to keyloggers or malware on your own machine, but a strong, genuinely private way to sync secrets across your own devices.
